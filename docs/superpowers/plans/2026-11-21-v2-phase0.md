# Plan: Mnemo v2 Phase 0 ("stop the bleeding"), branch `v2/phase0`

## Context
`docs/mnemo-v2-spec.md` is a single spec file, not a folder. It covers v2 **Phase 0**: stop hourly consolidation from deactivating, merging and pruning memories; make migrations really run; restore atoms that decayed away; move the ~28k `locomo-conv-*` eval atoms out of production; switch the vector index to HNSW; add regression fixtures. It adds no new features. Background is in `docs/rewrite-notes-2026-11-21.md`. The spec sets these rules: work on branch `v2/phase0`, make small commits, open a PR but don't merge or deploy, take a backup before writing to production, and follow dry-run → **STOP** → transaction → verify for every data change. Gates G1, G2 and G3 need Tom's reply before work continues. **No atom text or feedback text goes into the repo, commits or reports. Counts and ids only.**

## Step 0: Branch setup (right after approval)
- `git switch -c v2/phase0` from `main`. The uncommitted `docker-compose.yml`, `uv.lock`, `last_claude.sh` and `scripts/migrate_agents.sh` changes stay unstaged. They are local deployment changes and must not be committed.
- Commit `docs/mnemo-v2-spec.md` and this plan as `docs/superpowers/plans/2026-11-21-v2-phase0.md`, following the repo's plan convention. `docs/rewrite-notes-2026-11-21.md` stays untracked because it contains private feedback (Tom's decision).
- Push and confirm `[ahead 0]`. Stop there unless told to start work item 1.

## Work order
The code items (3, 4, 7, 6) can be built and tested against `mnemo_test` before anything touches production. Production items (1, 2, 5) run in spec order with the gates.

- Write the queries as one SQL file in the scratchpad and run it with `psql` from the production `.env` URL. Cover: per-agent total/active/inactive counts and status; inactive atoms split into merged (`access_log.metadata->>'absorbed_atom_id'`) vs other; consolidation runs per day over 60 days with their counts; `store_jobs` by status and oldest stuck job; `store_failures`; `decomposer_version` split; consolidation-source atoms; max/p99 of `confidence_alpha`; edges by type and self-loops; `decomposer_usage` rows and `sum(cache_read_input_tokens)`; `MNEMO_*` env var names; `schema_migrations` rows; whether `edges.metadata` and `lifecycle_dlq` exist.
- `grep "Consolidation run failed"` in `docker compose logs`.

### B. Backup (spec item 2)

- The confidence floor, when the flag is false:

  - `view_service.recall_shared`: skip the filter at line 442.
  - `view_service.recall_all_shared`: drop the hardcoded `>= 0.05` at line 591 but keep the `min_similarity` check.
  - `composite_score` ranking is unchanged.
- Tests: in `tests/test_consolidation.py`, existing tests monkeypatch `settings.*_enabled = True` for the step they exercise. Add a new test: with defaults, a faded atom, a duplicate pair and an edge to an inactive atom all survive `run_consolidation`. ### D. Migrations that really run (spec item 4)
- `mnemo/cli.py`: the CLI today is an HTTP client (click group `cli`). Add a `migrate` command that connects directly through asyncpg to `MNEMO_MIGRATION_DATABASE_URL`, falling back to `MNEMO_DATABASE_URL`. It lists `migrations/*.sql` in filename order, skips versions already in `schema_migrations`, applies each pending file and its `INSERT INTO schema_migrations` in one transaction, and has a `--dry-run` option. Reuse `_MIGRATIONS_DIR` from `migration_service`; add a shared `list_pending(conn)` helper there.
- `mnemo/server/services/migration_service.py`: replace the heuristics (lines 52–150) with `list_pending`. When migrations are pending, log an error naming them, and if `settings.require_migrations` (new setting, default True) is set, raise so startup fails (`main.py:36`). Keep the graceful path for a missing `schema_migrations` table, but treat it as pending.
- `schema.sql`: insert versions `001`–`005` into `schema_migrations`, since the file already contains their effects. 006 onwards come from `mnemo migrate`. Check that `schema.sql` doesn't already include 006 (edges metadata, `lifecycle_dlq`). If it does, reconcile so a fresh build matches production.
- 006 is already idempotent (`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`). Confirm the `ALTER TABLE edges` constraint drop/add at lines 8–11 is guarded too.
- New `migrations/007_deactivation_tracking.sql`:
  - `deactivation_reason TEXT`
  - `restored_at TIMESTAMPTZ`
  - `DELETE FROM edges WHERE source_id = target_id`
  - `edges_no_self_loop` CHECK constraint
- Test: a pytest that builds a throwaway database from `schema.sql`, runs `migrate` and asserts nothing is pending. Then a manual check: `pg_dump --schema-only` diff between a scratch database and production after 5a, recorded in the report.
- `mnemo_test` needs `mnemo migrate` run against it before the suite.
